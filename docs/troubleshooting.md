# Troubleshooting

Start with the audit - it answers most questions in one screen:

```bash
omv        # bin/verify.sh
```

```
   Omarchy registry: 87 plugins (first-party 38, third-party 49)
   plugins.txt: 49 declared (47 URL + 2 LOCAL)
   third-party: in bar 29 | services/panels 6 | disabled 15
   disabled (saved state, not an error): <ids...>
   shell: ping ok
   active theme 'gruvbox': complete (colors.toml + 8 wallpapers)
   patches: 2 applied, 0 to apply, 0 conflicts, 0 without plugin
   INVENTORY.md: present (generated by omx on the source machine)

   result: OK - this machine matches the repo
```

Lines starting with `!` are errors (exit code 1), `~` are warnings.

## Symptom -> cause -> fix

| Symptom | Cause | Fix |
|---|---|---|
| `error: The following untracked working tree files would be overwritten by merge` | a path is new in the incoming commits and a local untracked copy exists (autostash does not cover untracked files) | `pull.sh` handles it: local copies move to `backups/untracked-<ts>/`. To inspect first: `omr --keep-untracked` |
| `cannot pull with rebase: You have unstaged changes` | local edits in synced files (the shell rewrites `shell.json` on its own) | `omr` (autostash) or `omr --repo` (repo wins, local changes go to a stash: `yadm stash list`) |
| `Git repo does not exist. did you forget to run 'init' or 'clone'?` | that machine never got a yadm repo, so `omr` has nothing to read | `yadm clone --bootstrap <your-repo-url>` |
| `import.sh: unknown option --themes-only` on the other machine | it is running an older copy of the script, i.e. the pull never succeeded there | fix the pull first (`omr`), the scripts come with it |
| Theme loads but no wallpaper / missing from the picker | hollow theme (no `backgrounds/`) | `omr --themes-only --repair-themes`, or plain `omr` (auto-repair) |
| Bar keeps the old layout after `omr` | Quickshell held state in memory | `omr --restart-shell` |
| Plugin updater: `Dirty, untracked or ignored files present` | panel manager's strict guard vs runtime files in the plugin dir | use `bin/plugin-update.sh` (built-in updater); `--list-dirty` explains each directory |
| Plugin shows `enabled: true` but never `active: true` | the plugin directory lost its owner `x` bit | `chmod u+x ~/.config/omarchy/plugins/<id>` |
| A plugin is installed on the other machine but not enabled | for third-party plugins, absent from `shell.json` **is** disabled (see `docs/pitfalls.md` #6) | add it to `bar.layout.*` or `plugins[]` **on the source machine**, then `omx` |
| `verify.sh` reports a patch conflict | the plugin changed upstream and your patch no longer applies | update with `bin/plugin-update.sh`, then regenerate the patch on the source machine |
| Junk (`*.lock`, `*.bak*`) got committed | excludes were not in effect on that machine | `yadm rm --cached <path>`; `import.sh`/`export.sh` now set the excludes and `export.sh` has a guard |

## Recipes

**The other machine diverges and you want the repo version**

```bash
omr --repo            # local changes to a stash, repo wins
yadm stash list       # your local changes are still there
```

**You changed something on the wrong machine**

```bash
omr --no-import       # pull only
omv                   # see what now diverges
# take the repo version of one file:
yadm checkout -f -- .config/omarchy/shell.json
```

**Recover a file that was moved aside during a collision**

```bash
ls ~/.config/omarchy-desktop/backups/untracked-*/
diff -u ~/.config/omarchy-desktop/backups/untracked-<ts>/<path> ~/<path>
```

**Find out what is blocking a pull**

```bash
cd ~ && yadm status --short
yadm diff --stat HEAD..origin/main      # what is coming
```

**A plugin install fails**

```bash
omarchy plugin add <url> --yes     # run it by hand, the error is printed verbatim
```

Common causes: the URL is wrong, the network is down, or the plugin id is already taken by
another clone (`omarchy plugin list | grep <id>`).

## Known limits

- Plugins shipping prebuilt binaries (for example `runtime/bin/*`) may need a rebuild on a
  different architecture (x86_64 vs aarch64). The import reports the failure; build it manually.
- First import on a brand-new machine downloads every theme (hundreds of MB). Budget disk and
  time for it.
- Anything requiring a login (OAuth, keyring tokens) stays manual by design - see `manual.md`.
